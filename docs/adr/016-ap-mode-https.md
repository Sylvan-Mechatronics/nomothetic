# ADR-016: AP Mode Interface Binding (plain HTTP on 192.168.4.1)

**Status:** Amended (2026-05-11 — reverted from HTTPS/TOFU to plain HTTP)  
**Date:** 2026-05-09  
**Deciders:** Perceptua  
**Supersedes:** ADR-015 (Plain HTTP for Soft AP Pairing)

> **Amendment 2026-05-11:** The original ADR-016 decision adopted self-signed
> HTTPS with TOFU certificate pinning via `react-native-ssl-pinning` v1.x.
> This was subsequently reverted in full.  The amended decision (see below)
> restores plain HTTP but retains the ADR-015 interface-binding fix and the
> JWT signing secret persistence introduced in the original ADR-016.
> The original TOFU/HTTPS rationale is preserved below for historical context.

---

## Context

ADR-015 introduced a plain HTTP service (`nomothetic-ap.service`, port 8080,
`0.0.0.0`) for initial device pairing over the Soft AP.  Two issues with
ADR-015 remain unresolved:

1. **HTTP surface is broad** — the AP service binds to all interfaces
   (`0.0.0.0:8080`), so it is reachable from the home LAN if started
   while connected to Wi-Fi (ADR-015 risk R1).

2. **JWT does not survive mode switches** — `PairingState.jwt_secret` is
   in-memory only.  When the AP service stops and the Wi-Fi service starts,
   a new secret is generated, invalidating all AP-issued JWTs.  The user must
   re-pair every time the device transitions between modes.

## Amended Decision (2026-05-11)

Retain plain HTTP but adopt the following two fixes from the original ADR-016
scope:

- **Interface binding** — bind `nomothetic-ap.service` to `192.168.4.1` only
  (was `0.0.0.0`).  This resolves ADR-015 risk R1: the AP API is unreachable
  from other network interfaces.

- **JWT secret persistence** — change `PairingState.jwt_secret` from an
  ephemeral `secrets.token_urlsafe(48)` to a `DeviceJwtSecretStore`-managed
  value persisted at `/var/lib/nomon/device_jwt_secret` (`0600 nomon:nomon`).
  Both the AP and Wi-Fi services use the same on-disk secret.  JWTs issued
  during AP pairing remain valid after the device transitions to Wi-Fi mode.

Drop HTTPS, TOFU, `react-native-ssl-pinning`, the cert generation module
(`nomothetic.ap_mode.cert`), and the bootstrap service
(`nomothetic-ap-bootstrap.service`) entirely.

### Rationale for reverting HTTPS/TOFU

The TOFU/pinning approach was implemented then reverted for the following reasons:

1. **Threat model**: the AP is a WPA2 hotspot with a per-device PSK (since
   2026-09-13 a separate 20-character `ap_passphrase`, not the short pairing
   code — an 8-digit PSK is crackable offline from a captured handshake).  An
   attacker cannot join the AP without the PSK.
   Physical co-presence is already required, and the `192.168.4.1` binding
   ensures the API is not reachable from other networks.  The incremental
   security benefit of TLS in this context is negligible.

2. **Library limitations**: `react-native-ssl-pinning` v1.x (AFNetworking)
   ignores runtime SPKI hash strings on iOS and requires pre-bundled `.cer`
   files.  TOFU by design has no bundled cert.  The iOS code path would have
   to throw an explicit error, meaning AP mode pairing was effectively
   Android-only.

3. **Complexity cost**: the approach required a native Expo dev client build,
   an inline ASN.1 DER parser, a bespoke Expo config plugin, a second systemd
   unit, and cert lifecycle management (generation, rotation, expiry).  The
   complexity-to-benefit ratio is unfavourable for a fleet device in a
   physically-controlled environment.

### Service configuration

`nomothetic-ap.service` after this amendment:

```
ExecStart=... uvicorn nomothetic.api:create_app --factory \
  --host 192.168.4.1 --port 8080
```

No `ExecStartPre` (cert generation removed).  No SSL flags.  One unit.

`constants/config.ts` after this amendment:

```typescript
// The device AP API is served over plain HTTP, bound to 192.168.4.1 only.
export const SOFT_AP_URL = "http://192.168.4.1:8080";
```

`SOFT_AP_BOOTSTRAP_URL` (previously `http://192.168.4.1:8080`) is removed —
it is now the same address as `SOFT_AP_URL`.

Android `network_security_config.xml` (generated by `apModeTlsPlugin`) retains
the cleartext exception for `192.168.4.1` and the global cleartext-off default.
The iOS ATS exception for `192.168.4.1` (`NSExceptionAllowsInsecureHTTPLoads:
true`) is retained in `app.json`.

### JWT signing secret persistence (retained from original ADR-016)

`DeviceJwtSecretStore` (`src/nomothetic/device_jwt.py`) manages the on-disk
JWT signing secret:

1. Read from `/var/lib/nomon/device_jwt_secret` if the file exists, is
   readable, and contains ≥ 32 characters.
2. Otherwise, generate a new `secrets.token_urlsafe(48)` and write it
   atomically (`0600 nomon:nomon`).

`PairingState.reset()` calls `DeviceJwtSecretStore.rotate()`, which generates
and persists a new secret, invalidating all existing JWTs (factory reset).

## Security Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|----|------|-----------|--------|------------|
| R1 | ~~**AP API reachable from home LAN**~~ | Resolved | — | Service binds to `192.168.4.1` only. |
| R2 | **Cleartext AP traffic** — API calls and JWT in transit visible to co-present AP clients | Very low (WPA2 PSK limits attacker to physical co-presence) | Low | WPA2 PSK as proximity control; `192.168.4.1` binding prevents LAN exposure. |
| R3 | **JWT secret file readable by nomon processes** | Low | Medium | `0600` mode; rotate by deleting file + restarting service. |
| R4 | **Physical SD card extraction → secret theft** | Low (device in operator's possession) | High | Short-lived access tokens (15 min); document in operator guide. |

## Consequences

### Positive

- AP service binds exclusively to `192.168.4.1` — not reachable from LAN.
- JWTs survive AP → Wi-Fi transitions — no re-pair required.
- No native dependency in nomotactic — AP mode works on iOS and Android.
- No cert lifecycle management, no bootstrap service, no second systemd unit.
- Standard `fetch` in nomotactic — no bespoke HTTP wrapper.

### Negative

- AP traffic is not encrypted in transit; a co-present attacker on the AP
  network could observe API calls and JWTs.  Considered acceptable given
  WPA2 PSK physical-proximity requirement.

## Future

- **mDNS-based LAN pairing** — once mDNS hostname resolution is available,
  consider a Tailscale-backed or LAN-direct pairing flow that avoids the
  AP setup entirely for repeat visits.
- **Key rotation endpoint** — `POST /api/device/auth/admin/rotate-key`
  (operator-only) to force a new JWT secret without a full factory reset.

## Original HTTPS/TOFU Decision (superseded 2026-05-11)

*The following preserves the rationale for the original ADR-016 decision for
historical reference.  It is no longer in effect.*

Options re-evaluated at 2026-05-09:

1. **Maintain ADR-015** — fix the binding issue in the service file only,
   accept JWT invalidation as a "re-pair required" notice in the UI.
2. **Self-signed HTTPS on AP with TOFU bootstrap** — generate a dedicated
   self-signed cert for `192.168.4.1`, serve the main AP API over HTTPS port
   8443, and provide a minimal HTTP bootstrap service (port 8080) that
   delivers the cert PEM so the mobile client can perform TOFU cert pinning.
3. **Two uvicorn workers sharing the same cert** — single cert covering both
   `192.168.4.1` and the Tailscale FQDN.  Loses Tailscale Let's Encrypt certs.

The 2026-05-09 decision was **Option 2**, subsequently reverted as described
above.


### AP certificate

A dedicated self-signed certificate is generated once at
`/var/lib/nomon/ap-certs/{cert,key}.pem` with the following SAN list:

- `IP:192.168.4.1` (fixed Soft AP gateway)
- `IP:127.0.0.1`
- `DNS:localhost`

Generation is idempotent: the module skips generation if a valid cert already
exists (expiry > 30 days).  The cert is valid for 10 years, RSA 2048, SHA-256.
File permissions: `cert.pem` → `0644` (public), `key.pem` → `0600 nomon:nomon`.

This cert is completely separate from the Wi-Fi/Tailscale cert at
`/etc/nomothetic/tls/`, which continues to be provisioned by
`provision_tls_cert()` (ADR-001).

### Certificate bootstrap service

A minimal HTTP FastAPI application (`nomothetic.ap_mode.bootstrap`) serves
exactly two unauthenticated routes:

- `GET /api/cert` → cert PEM (`application/x-pem-file`)
- `GET /api/health` → `{ "status": "ok" }`

This service runs on `192.168.4.1:8080` (plain HTTP, no auth) as a separate
systemd unit (`nomothetic-ap-bootstrap.service`).  It is started and stopped
by `ap-mode.sh` alongside the main AP service.  No JWT, no device control,
no sensitive data.

The HTTP surface is explicitly limited to certificate discovery.  Delivering
a public certificate PEM over HTTP does not require TLS — the certificate
itself is not secret.

### AP main service

`nomothetic-ap.service` changes from:
```
--host 0.0.0.0 --port 8080  (no TLS)
```
to:
```
--host 192.168.4.1 --port 8443 --ssl-certfile ... --ssl-keyfile ...
```

The binding restriction to `192.168.4.1` ensures the AP API is unreachable
from other network interfaces even if `nomothetic-ap.service` is started
outside the `ap-mode.sh` context.

### TOFU flow in nomotactic

On first AP connection:

1. App calls `GET http://192.168.4.1:8080/api/cert` (bootstrap, HTTP).
2. App computes SHA-256 fingerprint of the PEM, displays it for user
   confirmation ("Trust this device?").
3. App stores the PEM in `expo-secure-store`.
4. All subsequent AP API calls go to `https://192.168.4.1:8443` using
   `react-native-ssl-pinning` v1.x with `pkPinning: true`.  The SPKI
   SHA-256 pin (`sha256/<base64>`) is derived at runtime from the stored
   PEM via an inline ASN.1 DER parser — no bundled `.cer` files required.
5. On subsequent AP connections (device already paired), skip step 1–3;
   load cert from `expo-secure-store` directly.

`constants/config.ts` exports two AP constants:

```typescript
export const SOFT_AP_BOOTSTRAP_URL = "http://192.168.4.1:8080";
export const SOFT_AP_URL = "https://192.168.4.1:8443";
```

`app.json` changes:
- Android: remove `usesCleartextTraffic: true`; add an Expo config plugin
  that generates `network_security_config.xml` allowing cleartext only for
  `192.168.4.1:8080`.
- iOS: update the ATS exception for `192.168.4.1` so that
  `NSExceptionAllowsInsecureHTTPLoads: true` is kept only for port 8080
  (cert bootstrap); HTTPS on port 8443 uses normal TLS with cert pinning.

### JWT signing secret persistence

`PairingState.jwt_secret` is changed from `secrets.token_urlsafe(48)`
(ephemeral, in-memory) to `DeviceJwtSecretStore.load_or_generate()`, which:

1. Reads the secret from `/var/lib/nomon/device_jwt_secret` if the file
   exists, is readable, and contains ≥ 32 characters.
2. Otherwise, generates a new `secrets.token_urlsafe(48)` and writes it
   atomically to the file (`0600 nomon:nomon`).

Both the AP service and the Wi-Fi service use the same on-disk secret, so
JWTs issued during AP pairing remain valid after the device transitions to
Wi-Fi mode.

`PairingState.reset()` calls `DeviceJwtSecretStore.rotate()`, which generates
and persists a new secret.  This invalidates all existing JWTs — consistent
with the existing behaviour on a factory reset.

### Clean module separation

```
src/nomothetic/ap_mode/
    __init__.py      — public exports
    cert.py          — create_ap_self_signed_cert(), get_ap_cert_fingerprint()
    bootstrap.py     — create_bootstrap_app() FastAPI factory
    server.py        — APServer class (wraps uvicorn, enforces 192.168.4.1 binding)
src/nomothetic/device_jwt.py
                     — DeviceJwtSecretStore
```

`api.py` route handlers are **not duplicated**.  `APServer.run()` calls
`create_app()` from `nomothetic.api` — the same factory used by the Wi-Fi
service.  The only difference is the uvicorn configuration (host, port, cert).

## Rationale

- **WPA2 as proximity control is unchanged** — an attacker still cannot join
  the AP without the WPA2 passphrase (a long random `ap_passphrase`, distinct
  from the pairing secret since 2026-09-13).  HTTPS adds a second
  layer: co-present clients on the AP network cannot eavesdrop on API traffic
  or JWTs in transit.
- **Minimal HTTP surface** — port 8080 serves only public data (the cert PEM).
  Sensitive operations (pairing, device control) are on HTTPS 8443.
- **TOFU is standard for offline/private systems** — SSH uses the same model.
  The user confirms the cert fingerprint once.
- **JWT persistence resolves a real UX regression** — without it, every AP →
  Wi-Fi transition requires re-pairing, which is confusing and error-prone.
- **`0600` file permissions are sufficient** — the threat model for a private
  fleet device does not require key encryption at rest.  Root can always read
  files; the mitigating control is device physical security.  This matches the
  existing pairing secret (`0640`) which is also unencrypted.

## Security Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|----|------|-----------|--------|------------|
| R1 | **HTTP port 8080 serves cert PEM** — cert PEM is not secret (public key), so leaking it over HTTP is harmless. | N/A | None | Cert PEM is designed to be public. |
| R2 | **TOFU window** — on first AP connection, the app fetches the cert over HTTP before pinning. A MITM during this window could substitute a different cert. | Very low (physical proximity required to join AP) | Medium | WPA2 PSK limits attacker to physical co-presence; user is prompted to confirm fingerprint. |
| R3 | **JWT secret file readable by nomon processes** | Low (nomon user is a system account; no user-facing shell) | Medium | `0600` mode; rotate by deleting file + restarting service. |
| R4 | **Physical SD card extraction → secret theft** | Low (device is in operator's possession) | High | Short-lived access tokens (15 min). Delete file to invalidate. Document in operator guide. |
| R5 | **Android cleartext config plugin is bespoke** | Medium (config plugin must be maintained) | Low | Target cleartext to `192.168.4.1:8080` only. |

ADR-015 risks R3 (broad `usesCleartextTraffic`) and R1 (HTTP port reachable from LAN) are resolved by this decision.

## Consequences

### Positive

- All AP API traffic (pairing, device control) is encrypted in transit.
- HTTP surface is reduced to one unauthenticated, public-data-only route.
- AP service binds exclusively to `192.168.4.1` — not reachable from LAN.
- JWTs survive AP → Wi-Fi transitions — no re-pair required.
- AP-mode code is cleanly isolated in `nomothetic.ap_mode` — testable and auditable.
- Android `usesCleartextTraffic: true` (global) is removed.

### Negative

- `react-native-ssl-pinning` v1.x adds a native dependency to nomotactic, requiring Expo dev client or bare workflow.
- TOFU adds one extra step to the first AP pairing flow.
- The `nomothetic-ap-bootstrap.service` is an additional systemd unit to manage.
- Operator must understand that deleting `/var/lib/nomon/device_jwt_secret` forces re-pairing.
- **AP mode HTTPS is Android-only** with `react-native-ssl-pinning` v1.x.  The library's
  iOS path (AFNetworking) ignores runtime SPKI hash strings and reads pinned certificates
  exclusively from the app bundle.  Since TOFU by design has no bundled `.cer`, the iOS
  code path throws an explicit error rather than silently bypassing pinning.  See Future
  for the resolution path.

## Future

- **iOS AP mode HTTPS**: adopt a library that supports iOS runtime certificate pinning
  (e.g., a custom native module, or evaluate `react-native-certificate-pinning`).
  Until then, AP mode pairing is unsupported on iOS and `fetchWithApCert` throws a
  descriptive `Error` on `Platform.OS === "ios"`.
- **Automated fingerprint display**: show the SHA-256 fingerprint on the Pi's
  display (if attached) or in the systemd journal so the user can verify it
  without the HTTP bootstrap endpoint.
- **Key rotation endpoint**: `POST /api/device/auth/admin/rotate-key` (operator-only)
  to force a new JWT secret and invalidate all sessions without a full factory reset.
- **mDNS FQDN in SAN**: include the device's mDNS hostname
  (`nomon-<last4>.local`) in the AP cert SAN, enabling name-based access once
  the client sets up mDNS resolution — useful for future LAN (non-AP) pairing
  flows without Tailscale.
